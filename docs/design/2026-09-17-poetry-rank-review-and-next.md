# 诗词升官：方案评审与 Zcode 执行任务

日期：2026-09-17。依据当前设计文档及代码检查；未做市场规模或用户留存验证。

## 评估结论

核心循环可作为原型推进：答题得到功名、解锁晋升挑战、取得称号。设计较完整，但不能直接按现稿实施。

1. 严格不重复：当前仅保存最近 40 个素材，且引擎只把旧题排后。原设计科考复用违反要求。会试、科考、每日题均不得重复已见题；重开、刷新、并发也必须纳入后续验证。
2. 有限题库不能同时承诺永久不重复和无限游玩。不足时明确返回内容不足，保留进度，等待扩容；不得回退旧题、越级借题或自动晋升。可复习的模式将来另议，不属于本次授权实现。
3. 难度应随官阶整体上升，不能仅凭 grade 断言每一道更难。保留学段作为初始标签，按题型、熟悉度、干扰项质量校准；高阶窗口重叠必须明确。首版承诺官阶难度档递增，不承诺逐题绝对递增。
4. 容量需按完整路径核算：现 computeScore 下每局十题全对且最快约得 2000 分，156000 至少 78 局、780 次作答（含计分科考）。失败、弃局也会消耗新题。800 首或每窗 150 个素材不是自动充分条件；须考虑窗口重叠、同题去重和晋升考试预留。
5. 数据完整性：后续需要原子选题占用、并发冲突重试、结算一次性记账、晋升条件重新检查、每日唯一约束。唯一 upsert 不等于并发发题不会重复；L1 缓存不能绕过数据库的最终去重判断。
6. 玩家身份：匿名 playerId 本身不等于身份凭证；现有加密不等于授权。跨设备恢复需额外机制，不能直接宣称可用。
7. 商业化暂缓。原稿广告额外次数/功名加成与不卖数值的表述矛盾。先验证答题升官闭环，再设计商业化。
8. 布衣到皇帝作为架空称号路线处理，文案避免宣称为真实官制；普通练习称游学或研习，避免所有阶段均称会试。

## 阶段与验收

### A：本次交给 Zcode 执行

- 更新原设计文档解决上述冲突，清楚区分已实现与计划。
- 建立只读题库容量审计脚本：真实统计每窗口可用且不重复的题目，考虑有效干扰项和实际题面去重；报告全对、80% 与60% 正确率场景的估算与假设、失败/弃局风险。不伪造真实用户模拟结论。
- 明确题目规范身份：至少稳定 poemId + lineIndex + questionType；相同题面不可通过换 ID 绕过去重；整首诗可在不同知识点再出现，不能把严格去重暗改为同诗永不出现。
- 实现 rank.ts、promote.ts 等纯逻辑，保留旧玩法接口兼容；新增官阶严格出题入口，不能悄悄改变其他模式。
- 题量不足返回明确且可由上层识别的结果；不得返不足十题并当正常试卷，不得自动晋升或借更高档题。
- 单测覆盖：边界经验、考试目标必须是下一阶、经验不足不能升、失败保留经验、普通练习不能升、最高阶/皇帝一致、排除所有已见、题面重复、容量不足、种子确定性、旧模式兼容。
- 运行 npm.cmd test、npm.cmd run lint 和 TypeScript 检查；报告基线失败与本次新增失败，不能把静态测试冒称浏览器验收。
- 交付变更文件、测试结果、容量报告、剩余阻塞。允许报告题库容量不够，但不能放宽规则假装通过。

本阶段不改真实数据库，不接广告支付，不扩充未经核对的题库，不提交或推送 git，不删除其他玩法，不修改 .env/凭据。保留所有既有未提交文件。
